# M3 browser boundary decision

Install the browser matching the root Playwright Test package with `npx playwright install chromium` before running the browser integration tests. The M3 validation used Playwright Test 1.63.0 and its Chromium build 1243.

The production browser boundary uses one `ProtectedContextFactory` for exploration, locator validation, and deterministic replay. Each call resolves an immutable profile ID/version and its referenced network policy, starts a local address-pinning proxy, launches a fresh Chromium browser through that proxy, and creates one disposable context. Sessions expose the effective profile fingerprint and Node, Playwright, and browser versions. Callers close the session to close the context, browser, proxy listener, and sockets.

The network policy has exact hostname, port, and IP-address allow rules. The proxy resolves each HTTP request, CONNECT tunnel, and WebSocket upgrade separately. It rejects any unlisted destination or changed DNS answer and connects to an approved IP literal, so a second DNS lookup cannot change the actual destination. Browser proxy settings force loopback requests through the policy; service workers are blocked. Session start verifies that a denied loopback canary returns the proxy's policy response without reaching its local server. Main/iframe navigation, redirects, subresources, fetch/XHR, WebSocket handshakes, and download requests are covered by the same destination check. No direct-network fallback is configured. Other browser engines are rejected at profile validation until their egress behavior has equivalent evidence.

The profile records an auth-state ID/version only. A protected provider supplies storage-state contents at session start; those contents are not returned as profile metadata. The catalog holds settings in memory for M3; M5 owns durable artifact storage. A changed profile or policy under an existing reference is rejected when compared with the recorded effective fingerprint. The network policy intentionally requires explicit destination configuration; intake and policy administration are later work.

M8-B fails session creation for any non-loopback destination unless a trusted `ExternalTargetGate` authorizes the effective profile before browser startup or auth-state loading. Without that gate, local fixture policies remain usable and external targets remain closed pending security review. A rejected gate never starts a browser. Session closure tears down context, browser, and proxy; a proxy failure does not create a direct-network fallback.

Browser integration tests use two local servers to prove that approved traffic arrives and denied navigation, redirects, frames, subresources, fetch, WebSockets, and downloads do not reach the denied server. Separate tests exercise CONNECT, DNS-address changes, missing profiles/policies/auth, context isolation, and resource cleanup. The browser must run in a restricted host environment before arbitrary untrusted targets are admitted, as required by the architecture's later security review.
