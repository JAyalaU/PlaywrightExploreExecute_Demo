# Deterministic boundary reality

Scope: the selected `structured-action-v1` route, TestSpec v5 → SuccessfulExplorationTrace v4 → CompilerAttempt v3 → ResolvedTestSpec v8 → deterministic v8 runner. This is a code and contract audit, not a live-provider result. The v4/v3/v7 and released v2/v6 routes are relevant only where they supply reused types or explain an upward constraint. `docs/system-overview.md` still describes v2/v6 as the released baseline; `docs/current-status.md` and the current implementation describe the structured route as an offline-gated candidate awaiting real-provider proof.

## Exact execution boundary

`compileSuccessfulTraceV4` reads immutable TestSpec v5 and trace v4, opens a **different protected browser session**, repeats the successful path in order, and either persists a typed rejected CompilerAttempt v3 or an accepted attempt with v8. It does not consume an M7 claim as replay authority. Readback validates the source, attempt, trace, protected observations/witnesses, compiler record, and resolved artifact together. `AcceptedResolvedTestSpecV8.fromStore` mints the runner input after that readback; `executeResolvedTestSpecV8` refuses raw JSON or another version and checks the approved profile fingerprint before opening a fresh session. The runner uses accepted locator forms, actions, and assertions without M7 or MCP repair. [Compiler](../../app/exploration/trace-compiler-v4.ts), [v8 contract](../../app/domain/structured-action-compiler.ts), [accepted capability](../../app/evidence/accepted-v8.ts), [runner](../../app/runner/run.ts).

Trace v4 retains the v3 ordered action and verification path, source/profile/session and state digests, current-state bindings, and completed authored step IDs. It adds exactly one requested-intent/selected-witness proof per authored click, fill, or select. A trace verifier compares the requested intent to the stored TestSpec, the witness to a protected runtime source, and both to the selected binding, operation, frame, epoch, and state. Discovered prerequisites have their own binding and path record, never an authored action proof. Verification records preserve the chosen comparison, trusted observation IDs/results, action ordinal, evaluated truth, and optional temporal linkage. [Trace schema and validation](../../app/domain/agentic-trace-v3.ts), [base path and binding](../../app/domain/agentic-contracts.ts), [witness](../../app/domain/action-identity-witness.ts).

Compiler v3 requires a distinct fresh session, matching execution profile/fingerprint, ordered postcondition checks, fresh identity and selected-target checks for targeted steps, and fresh verification-strategy correspondence. Rejection has a failed check and no accepted action/assertion links; acceptance has a checked resolved step for every successful path record. Compiler failures and unsupported representation yield no v8 and no QA verdict. [Compiler attempt validation](../../app/domain/structured-action-compiler.ts), [compiler execution](../../app/exploration/trace-compiler-v4.ts).

## Where exploration cannot become v8

1. **Temporal transition:** the v4 trace can validate a genuine earlier observation, intervening actions, and later observation with `appears`/`disappears`. `assertionFromStrategyV1` returns no predicate for `transition`; the compiler rejects `UNSUPPORTED_TEMPORAL_REPLAY`. A final-state count is deliberately not substituted. [Trace temporal checks](../../app/domain/agentic-trace-v3.ts), [projection](../../app/domain/goal-directed-compiler.ts), [compiler](../../app/exploration/trace-compiler-v4.ts).
2. **Relative/spatial relationship:** a VerificationGoal can carry `above`, `below`, `before`, or `after`, but successful-trace validation explicitly rejects relationship intent. V8 has no relationship assertion. This fails before compilation even if a model could infer it from a snapshot. The compiler's `UNSUPPORTED_RELATIONSHIP` reason exists in its schema, but this route cannot ordinarily produce a valid relationship trace. [Goal schema](../../app/domain/verification-goal.ts), [trace guard](../../app/domain/agentic-trace-v3.ts), [assertion schema](../../app/domain/goal-directed-compiler.ts).
3. **Unnamed or context-only action target:** M7 might recognize and act on a unique current ref, but v5 requires an authored, nonempty exact accessible name before exploration; fresh compilation also rejects an empty selected name and projects exact role/name. A role-only, index-based, nearby-label, or arbitrary relational action identity cannot become v8 under this route. [Intent](../../app/domain/action-target-intent.ts), [fresh reconstruction](../../app/exploration/trace-compiler-v4.ts), [v8 validation](../../app/domain/structured-action-compiler.ts).
4. **Model-discovered target with no durable cross-context proof:** a session-local ref, unproven frame ancestry, nonunique fresh scope/target, or changed destination is insufficient. Those are reproducibility checks even when the exploratory click succeeded. [Compiler reconstruction](../../app/exploration/trace-compiler-v4.ts), [runner scope binding](../../app/runner/run.ts).
5. **Source data references in fill/select:** the shared source and replay schemas allow `dataRef`, and the runner has a data provider, but v4 fresh compilation performs the operation only for a string value and marks other values `UNSUPPORTED_REPRESENTATION`. This is a current producer/consumer gap, not a claim that a referenced value was proved end to end. [Source](../../app/domain/schema.ts), [compiler](../../app/exploration/trace-compiler-v4.ts), [runner](../../app/runner/run.ts).

## Backward constraints and answers

1. **Is the deterministic language appropriately small and generic?** For current final-state QA it is small and composable: ordered actions plus role/name/scope/frame queries and count/property/URL predicates. It is intentionally closed for reproducibility. Its actual coverage is narrower than the verification intent language: temporal and relationship claims cannot be reproduced. The fixed legacy two-link assertion is a case-specific exception in the shared union.
2. **Has replay vocabulary leaked upward into TestSpec interpretation?** Yes, partly. `VerificationGoal` keeps natural-language clause and optional hints, leaving the model to choose a strategy later, but v5 action interpretation must already supply exact accessible name, role mode, semantic scope, and literal spans. Those fields closely match the fresh compiler's role/name locator construction. The `select_option` value is structurally separate from target, which is appropriate; the target identity still must be named before M7 explores.
3. **Are there identity assumptions only because the compiler needs them?** The mandatory authored name and exact role/name/scope projection are needed by *this* compiler's proof method, not by a session-local exploratory ref. A durable, uniquely checked identity is necessary for reproducibility; a pre-exploration authored accessible name specifically is not established by the exploration mechanics. The same exact-name dependency also applies to discovered prerequisites when compiling them.
4. **Which semantics are genuinely necessary?** Source/profile provenance, ordered operations and arguments, selected-target correspondence, fresh uniqueness, durable frame/scope reconstruction, preserved predicate and expected value, and independent fresh replay are necessary to avoid changing the test or turning an exploration observation into QA truth.
5. **Which semantics are required prematurely?** The interpreter must resolve target accessible name, exactness, role mode and named scope, with source spans, before browser inspection. It must choose `click` versus `select_option` and separate an option value from the control's identity before M7 can inspect the dropdown. Requiring source spans is an interpretation-fidelity safeguard; requiring a concrete target name at that stage limits discovery.
6. **Does action identity overfit named accessible controls?** Yes. `accessibleName` is mandatory nonempty, fresh compilation insists on nonempty selected name, and v8 action locators are exact role plus name, optionally scoped. `role: unspecified` postpones the exact role only within a fixed operation-specific set; it does not permit unnamed identity. The v8 runner can technically bind a generic locator form, but v8 validation prevents using another authored action identity.
7. **Can `select_option` represent target separately from option/value?** Yes at the type and replay layers: the action has a control target/locator and separate `value`, and replay calls `locator.selectOption(value)`. That does not imply the interpreter can correctly parse a short phrase such as “Select Option 1”: v5 requires a named combobox target and an independently grounded argument before exploration. A named dropdown with a separately specified value fits the current shape; an unnamed dropdown or a phrase naming only the option does not. The compiler does not inspect the option list or prove an option-to-control relationship; it replays the preserved value against the freshly identified combobox.

The current architecture leaves a place for another phrase-driven patch if a request is forced into a v5 `actionTargetIntent` before the browser reveals the target. V3 compilation removed historical English parsing from the compiler; it did not remove the need for the interpreter to express exact role/name/scope in the source contract. A new wording pattern could therefore be accepted or rejected by interpretation/fidelity logic without adding a general target-discovery representation. This is a boundary observation, not an implementation proposal. [Fidelity rules](../../app/domain/action-target-intent.ts), [v5 requirement](../../app/domain/schema.ts), [v3 compiler](../../app/exploration/trace-compiler-v4.ts).

## Deterministic capability boundary

Successful exploration becomes a reproducible v8 test when every authored action has a v5 requested intent and protected identity witness that a fresh compiler can reconstruct as one exact named semantic target in a durable frame/scope, every prerequisite has its own reproducible binding, every operation and argument are preserved, and every verification strategy projects exactly to a fresh-evaluable count, unique property, or URL predicate. The deterministic runner then evaluates that accepted artifact in fresh contexts. Exploration that depends on an unnamed/context-only action target, an unproven or nonunique cross-context identity, a temporal or relational verification claim, or an unsupported action value representation cannot currently produce an accepted v8 artifact; those stops are not QA failures.
