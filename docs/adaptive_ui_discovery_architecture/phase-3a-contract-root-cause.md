# Phase 3A requirement and verification contract root cause

**Scope:** Read-only review of current adaptive source and the bounded facts supplied for the latest Activity and Security attempts. No provider call, live retest, implementation, prompt, schema, test, or budget change was made. The retained projection does not contain the model's raw proposal, the accepted plan values, or the full action witnesses; findings below keep source-proved behavior separate from live-run unknowns.

## 1. Proven causes and remaining hypotheses

| Finding | Status | Evidence and limit |

The reported field error is consistent with an intake-shaped URL predicate in a verification proposal, but the missing raw response prevents asserting its complete contents. |
| Security's g3 required action was not proved despite a recorded check | Proven only at coverage level | The supplied projection says an action receipt existed, its coarse effect was `control_changed`, and g3 stayed inconclusive. It does not retain enough witness, before/after, dependency, or accepted-predicate detail to identify the failed proof condition. |
| Repeated true checks of g3 could not establish g3 | Proven in source | `verificationMatchesAcceptance` returns false for every `required_action` goal. The three checks therefore could not satisfy g3 even if the observed checkbox state was true. The supplied projection confirms their mismatch. |
| The model inferred that another verify would repair g3 | Hypothesis | The controller exposed g3 as unresolved and the proposal schema allowed a verify bearing its goal ID. What the model inferred from that context and delivered feedback is not retained. |

The Security fixture's enabled state and g4's matching, explicit assertion check prove neither g3 action causality nor clean execution. Both attempts stopped before a clean pass.

## 2. Predicate representations and their relationships

| Boundary | URL/path | Element state | Other cases |
|---|---|---|---|
| Requirement intake and admitted acceptance plan | `{kind:'url', comparison:'equals'|'path_equals', value}`. `value` is a full allowed-origin URL for `equals`, or `/path` for `path_equals`. | `{kind:'element', role, name, property, equals}` with stable semantic identity. | `exists` and `count` require complete observation when establishing absence or exact count. Constraints and required-action operation/dependencies are separate. |
| Operational `verify` proposal | `{kind:'url', equals: full URL}`. | `{kind:'element_state', target, property, equals}`. `target` is a current browser target; only visible, enabled, checked, and value are expressible. | A visual proposal exists but the deterministic `verifyProposal` result is unknown. There is no operational count or existence predicate. |
| Proposal-to-acceptance match | Exact URL compares directly; path compares the proposed URL's origin with the current origin and its pathname with accepted `value`. | A role/name target, or an element ref resolved in the before observation, must match the admitted role/name/property/expected value. | The matcher immediately rejects required-action goals regardless of predicate equality. |
| Independent verifier | Evaluates admitted URL/path directly on trusted observations. | Evaluates admitted semantic element predicates directly; existence/count retain completeness rules. | Required actions additionally need historical action proof; constraints have their own evidence checks. |

The intake adapter sends a **strict structured output schema derived from the local intake contract** and parses the response against that same contract ([openai-reasoning.ts](../../app/adaptive/openai-reasoning.ts)). Operational proposals instead request generic `json_object` output and are then locally parsed as `AgentProposalV1` ([contracts.ts](../../app/adaptive/contracts.ts)). The model-facing proposal instructions show an `element_state` verification example but no URL verification example. There is no evidence of a disagreement between the intake provider schema and its local parser. The mismatch is between two intentional roles: stable acceptance meaning and observation-bound operational checking. The different field names and the absent model-facing URL mapping leave that relationship underspecified. Adding permissive aliases would hide the distinction between a path condition and a full-URL observation.

One canonical predicate schema would remove shape translation but must also represent current target binding, path versus full URL semantics, complete-domain count/absence, and visual uncertainty. That is a wider contract change. Deterministic conversion from admitted predicates to operational checks is narrower for supported URL and present named-element states, but does not cover count/existence or an absent target whose accepted predicate is `visible:false`. The smallest coherent direction is to keep distinct contracts while making their semantic relationship explicit and controller-derived: an operational check refers to an admitted goal/predicate identity, and code derives or evaluates the supported current observation form. Unsupported conversions receive a closed reason; the model does not invent an alias or redefine acceptance.

## 3. Required-action proof and the g3 gap

For a recorded check to prove its authored action, the goal must be grounded and at least one receipt must satisfy **all** of these conditions in [the independent verifier](../../app/adaptive/requirement-acceptance.ts):

1. Receipt goal ID and operation match the admitted action; delivery returned, an observed effect exists, and an after-observation ID exists.
2. Source and after observations are present in one execution session, in increasing observation order, with receipt URL and document revisions matching both snapshots.
3. The target witness binds to the source observation and to one observed target. Its encoded validated target and demonstrated reusable target must be consistent. For check/uncheck, the witnessed control must correspond to an admitted element predicate for that goal.
4. The goal's aggregate admitted predicate evaluation was **false before** and **true afterward**. The false aggregate can arise from one false predicate; it does not require every predicate to be false. A correct final checked state or a generic changed-control receipt cannot replace this transition.
5. Each authored `afterGoalIds` predecessor has its own valid proof in the same session, earlier in action order, with its completion observation no later than this action's source observation. Standalone required-order constraints also use proved actions.

`actionRecorded:true` says only that a receipt with that goal ID was logged. `effect:control_changed` is a coarse diagnostic category, not proof that the admitted checked predicate changed from false to true on the witnessed target. `missingActionEvidence:true` on a g3 **verification** checks required actions *earlier in source order*; it does not diagnose g3's own receipt. `progressAfter.coverage:inconclusive` establishes the coverage failure but not which proof condition failed. The retained projection lacks the accepted g3 predicate and dependencies, exact effect, target witness, and before/after predicate states, so the specific Security failure is unknown.

## 4. Verification semantics and progress

An operational `verify` can explicitly satisfy an outcome or assertion when its typed check matches admission, observes true, and independent coverage is `verified_true`. It **cannot** prove a `required_action`: [the matcher](../../app/adaptive/vertical-slice.ts) returns false before comparing the predicate. Required-action completion is computed from action evidence; a separate explicit verify is not required for it. The proposal instructions already ask for typed checks for outcomes and assertions, but the proposal schema and gateway accept a `verify` carrying any unresolved goal ID. The controller sends one undifferentiated `unresolvedGoalIds` list, which includes an action goal when its proof remains inconclusive. That combination permits the repeated g3 request; it does not establish the model's private reasoning.

For each accepted check, the controller computes observed true/false/unknown, acceptance match, coverage before and after, whether preceding required actions or an order constraint lack proof, and a closed feedback reason. It sends the latest four records on the next proposal context, and the adapter includes them in its model request. In the supplied Security attempt, previous feedback was delivered. A g3 check observed true but matched false, so `predicate_mismatch` takes precedence over any missing-action reason. Feedback does not say **“this goal kind cannot be verified”** or identify the failing proof condition. `newEvidence` means a first-seen normalized check outcome, not a new causal transition. Repeats increment the bounded ineffective counter after the model has received negative feedback; the stop is not an early assertion of QA failure.

There was no legitimate **verification-only** path to complete g3. The available operations still included browser actions, so a repair was theoretically possible if the missing proof could be re-established from a false before state and valid dependencies. With a checkbox already true, another check alone cannot meet false-to-true proof; restoring an authorized false state and checking again might be possible in some applications, but the controller neither identified the failed condition nor guaranteed such a route. If a prerequisite proof failed, repairing that chain would be necessary. An incompatible `verify` should receive a closed, informative response; an identical repeat can be rejected before another redundant observation under the existing repetition limit.

## 5. Evidence lifecycle and generalization

Exploration evaluates required actions against the full observation/action history on each turn. Their proofs use the receipt's own before/after snapshots, so later navigation does **not** erase a valid earlier menu-opening or navigation proof merely because its control disappears from the current page. Grounding promotion also considers accumulated observations. Outcome and assertion coverage instead evaluates the latest observation; explicit verification is additionally required when **all** goal predicates are operationally eligible under the current URL/non-count/non-existence condition. A goal containing an existence or count predicate is exempt, even if it also contains another predicate. Exploration may hand off only when all goals have coverage and required explicit checks. The learned procedure is provisional. Final verification uses separate clean-browser observations and clean executor receipts after reset and reload; exploration checks and model claims cannot establish final completion.

| Generic workflow | Positive evidence | Negative case that must remain incomplete |
|---|---|---|
| Click a link, verify destination | Witnessed click with path false before/true after; separate destination check when it is an assertion. | Destination already correct but required click omitted or invalid. |
| Open a menu, click its newly revealed link | Menu receipt proves a newly observed control; link receipt proves navigation and depends on the proved menu action. | Final destination reached with menu action missing, invalid, or out of order. |
| Change a checkbox, verify state | Witnessed check changes admitted checked predicate false-to-true; later assertion observes true. | Checkbox ends checked without a proved check, or a true check is misused as proof of the required action. |

## 6. Smallest contract-level corrections to test next

1. **Make the accepted-to-operational predicate mapping explicit and closed.** Prefer a check request tied to an admitted predicate identity, with deterministic evaluation/conversion for URL/path and present element states. Define count/existence and absent-target visibility behavior explicitly. Preserve acceptance as independent authority. Do not add permissive JSON aliases.
2. **Separate action-proof progress from assertion-check progress in model context.** Expose unresolved required actions as needing causal evidence and checkable outcomes/assertions as separate sets. Reject or return a closed `required_action_not_checkable` result for a verify addressed to an action goal before repeating observations. Keep the existing repetition budget.
3. **Expose a bounded proof-failure reason from the existing verifier.** The same proof evaluation that decides coverage should identify whether no receipt, goal/operation mismatch, witness, before/after linkage, false-to-true transition, or prerequisite proof is missing. This is diagnostic/decision feedback, never model authority or a lower proof standard. Do not infer a particular reason for the unretained Security receipt.

Offline tests should exercise strict intake/proposal parsing and semantic mapping for path/full URL and named element state; reject intake-shaped URL JSON at the proposal boundary with a precise closed error; prove that action-goal `verify` cannot advance coverage and receives the specific ineligible-goal signal; show negative feedback leads to an action choice rather than repeated checking; distinguish each action-proof failure with generic receipts; and confirm the three workflows above complete exploration only with all authored action, ordering, assertion, and explicit-check evidence. Negative tests must keep correct final state with omitted or invalid required actions inconclusive. A separate clean-run test should prove exploration evidence cannot substitute for clean execution.
