## Phase 1 vertical slice

- `app/adaptive/browser.ts` owns one protected native schema-5 Chromium page. It opens the approved local URL, collects an accessibility snapshot and at most 100 visible control facts (role/name/checked/enabled/value), issues session/page/observation/revision IDs, and re-reads the live page immediately before action dispatch. References are observation-scoped. It uses Playwright on the protected context directly because bounded DOM facts and native checkbox setting are needed; the existing MCP wrapper does not expose those as a single safe observation/action pair. Screenshots and coordinate dispatch remain disabled.
- `app/adaptive/openai-reasoning.ts` is one provider-neutral `ReasoningModel` implementation using a stateless OpenAI Responses JSON turn. It receives the immutable instruction and authored goals, the current bounded browser observation, recent action outcomes, unresolved goals, operation set, and remaining budget. It validates provider JSON with `AgentProposalV1Schema`; no provider output becomes browser authority. No Bedrock or second model is present.
- `app/adaptive/vertical-slice.ts` runs the bounded observe–reason–validate–act–observe loop. The Phase-0 gateway checks each proposal; the protected page owner rechecks URL, DOM/accessibility revision, target visibility, and actionability before Playwright click/check/uncheck or navigation. Model turns, browser actions, elapsed time, and repeated ineffective actions have trusted limits. Actions yield bounded evidence with post-observation references and a concrete URL/control transition when one is observed. A browser action exception retains an `unknown` delivery receipt; a returned action whose post-observation fails retains a returned receipt without claiming an effect. Recent model history associates each action with its actual after-observation ID.
- Demonstrated actions with observed effects are converted to `LearnedProcedureV1` steps using role/name strategies (or a proved in-scope URL for direct navigation), goal references, expected transitions, and evidence IDs. Live element refs are not persisted in the procedure. The Phase-0 action, trace, and procedure schemas were minimally extended to represent demonstrated navigation. After exploration, the controller closes that session, opens a second protected context, invokes the trusted application reset, verifies the reset proof, re-observes and re-resolves each step, and stops on target drift or a transition different from exploration. The clean pass reloads before independent outcome checks to distinguish persisted state from a transient checkbox.
- Exploration completion uses browser-evaluated typed `verify` proposals and observed action evidence to track unresolved authored goals. Fixture acceptance rules do not enter model context or exploration navigation. Independent clean verification uses trusted goal rules against clean browser observations and clean action evidence. Required actions need a delivered, observed action; outcome and assertion rules read current browser state after reload. Missing rules yield `INCONCLUSIVE`; observed false requirements yield `VERIFIED_FAIL`. Model completion cannot issue verifier evidence. The closed result contract validates trusted evidence refs and clean-start proof.
- `tests/support/adaptive-fixture.ts` has two local, resettable presentations: a direct Account settings link and a Profile menu that reveals Settings. Reset changes server-side notification state, so a fresh browser alone is insufficient. `tests/adaptive-phase1.spec.ts` drives both presentations through the real protected Chromium browser with an observation-dependent scripted model. Negative tests cover malformed/absent/stale/out-of-scope/unsupported proposals, budgets, ineffective repetition, browser/reset/action failures, unsupported procedure completion, clean target drift, false persisted outcome, cleanup failure, and reset freshness. These tests are included in `npm test` and never call a provider by default.
