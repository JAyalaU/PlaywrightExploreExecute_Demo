## Scope and evidence path

The local resettable fixture now has three presentations of the same goal: “Open my account settings, enable email notifications, and verify that email notifications are enabled.” A exposes an Account settings link; B exposes Profile, then Settings; C exposes an unnamed visible gear icon. The C gear shifts horizontally after the trusted server reset. The model receives the authored goal and live observation only. Fixture variant, selectors, coordinates, reset oracle, and expected sequence stay outside its context.

The observation broker collects URL, page title, bounded visible controls, accessibility snapshot, viewport, and session/page/document IDs. A screenshot request captures only the viewport as a bounded JPEG. The current screenshot bytes are held by the browser owner and passed to the OpenAI Responses adapter as an actual `input_image` alongside the compact observation text. Image turns are rejected for unrecognized model families. The configured `gpt-6.1-sol` is listed with image input and the Responses endpoint in the [official model card](https://developers.openai.com/api/docs/models/gpt-6.1-sol); provider access and actual image reasoning still require a credentialed live call.

The visual proposal target has `screenshotRef`, `coordinateFrameId`, viewport, bounded `x`/`y`, `description`, and spatial `context`; the interaction also names its operation, goal, and predicted effect. The gateway checks current observation and screenshot identity, session/page/document binding, screenshot age, viewport and coordinate bounds, click-only visual dispatch, budgets, and trusted risk permissions. The browser checks live URL, document facts, accessibility snapshot, viewport, scroll, and screenshot pixels immediately before action. It recovers a named semantic control when one is available; otherwise it uses guarded Playwright mouse click. The click return is followed by a new browser observation, and only an observed state transition becomes action evidence.

The learned visual procedure keeps `visual_anchor` description and context, goal ID, and observed transition. It carries no pixel coordinates. In clean execution, a fresh browser and trusted application reset are verified, a fresh screenshot is captured, and one constrained call to the same reasoning model re-identifies the anchor. The new proposal must cite the new screenshot and preserve the learned anchor, operation, and goal. The gateway and browser validate it again. Failure to re-identify or to observe the expected transition blocks the clean pass. The independent verifier reads clean actions and final browser state after reload; model self-report and a returned visual click cannot issue `VERIFIED_PASS`.
