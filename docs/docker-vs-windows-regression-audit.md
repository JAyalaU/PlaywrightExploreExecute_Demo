## Root lifecycle and semantic deltas

```text
Known-good Docker:
  Python host -> Node provider primary/fidelity -> factory.open Docker/CDP
  -> MCP in-memory connection/contextGetter -> exploration page creation
  -> bootstrap page.goto(start URL; Playwright default load)
  -> grounding session/tracker listeners -> initial protected state
  -> authored root navigation page.goto(same URL; default load)
  -> trace state -> first candidate query (frame.content + whole-body ARIA,
     role locator count, targeted ARIA/ref/actionability, fresh state)

Current local Windows:
  same provider path -> factory.open local chromium.launch
  -> MCP connection/contextGetter -> readiness tracker before page/navigation
  -> bootstrap page.goto(start URL; current MCP navigation semantics)
  -> grounding session with shared tracker -> initial protected state
  -> matching canonical nonredirected authored root navigation adopted
  -> trace state -> asynchronous readiness probe + first candidate query
     (frame.content, no whole-body ARIA for poc_v1, diagnostic select/role counts,
      same authoritative role predicate and targeted ARIA/ref, fresh state)
```

`app/interpretation/deferred-action-production.ts` owns bootstrap/adoption; `app/exploration/mcp.ts` owns page/navigation; `app/exploration/action-candidate-grounding.ts` owns query/state; the new readiness tracker is attached before bootstrap so it can observe root response and lifecycle on a future run. Docker baseline reloaded the root for the authored step; current matching-URL PoC makes one root document request. That is an intentional later performance fix with a real semantic difference: the first candidate sees the bootstrap document and whatever state accumulated during it, not a second freshly loaded document. It cannot alone explain a valid `/dropdown` native select disappearing after a click, but can explain a root-specific difference. Local viewer capture can start while page is `about:blank` or navigating. Readiness probes are launched without await, so they may overlap candidate reads. Navigation adoption requires same canonical URL and no redirect; it does not accept a redirect or change target matching. A local root run with `document.readyState=complete` and zero links also had an unobserved root response because the tracker attached late in that run; `complete` can describe an error document. A `chrome-error:` frame was recorded.

Exploration candidate enumeration still maps admitted `dropdown` to `combobox`/`listbox`, uses exact name only when admitted, then proves unique ref, frame, visibility/actionability and native option mapping. The PoC state digest now hashes bounded frame content and frame identity/URL without whole-body ARIA; historical mode retains ARIA. This deterministic change can remove an ARIA API failure; it cannot by itself turn `getByRole('link').count()` or native `select` inventory from positive to zero. The same admitted step-4 role/constraint digest produced one native select in one local run and zero in another. The failed root link query had zero **before** exact-name filtering; its predicate digest matched a prior local run with 46 links. These are runtime/document differences at observation time, not demonstrated interpretation drift. Generic click delivery, URL-only observation, selected-option verification, targeted ARIA/ref proof and current-state freshness are otherwise inherited from baseline; no changed predicate or option-verification semantics explain intermittent zeros.

Compiler v4 now adopts matching bootstrap navigation and records it, but keeps fresh target correspondence and option checks. Runner v9 also adopts matching root, switches both `goto` calls from default `load` to `domcontentloaded`, retries only a missing/nonactionable **first** target for the profile wait, and adds timing/diagnostic wrappers. Its `rich_after_url` still reads each frame's `content()` and `runner_v9_state=` body text after a URL-only assertion, before select proof. The retained replay-1 stop occurred precisely in this pre-action ownership/rich-state interval, with no select invocation and no replay 2. That is plausibly another symptom of an unstable/incomplete document or browser read; the stored record does not identify the failing API and cannot establish the same cause as a completed zero-candidate enumeration. Later runner diagnostics can classify a recurrence. Neither stop is a QA assertion failure.

Record passive main-document request/response status class, redirect, commit/failure, DCL/load, owned page/frame generation, and link count at the same readiness boundary. 2. Same current **local** code and read-only root/destination fixture, with active viewer/diagnostic browser operations enabled versus disabled, holding navigation and candidate logic fixed. This requires a later explicit diagnostic toggle and passive-only logging; compare capture/read latency and candidate counts. It tests protocol/timing pressure, not provider behavior.
3. From the **exact Node workflow process/environment** versus the direct provider-contract process, issue the same bounded primary request with private closed transport diagnostics (no browser). Vary only process launch topology. This distinguishes effective environment/transport differences; it requires separately authorized provider use and is not part of this audit.

## Classification

**`DOCKER_REMOVAL_CONTRIBUTING_SUPPORTED`**. The migration necessarily changed the browser OS/process/network/transport and physical presentation, and failures cluster at browser document/read boundaries after that change. Yet post-migration navigation adoption, runner wait policy and active observations are confounders; the stored public records lack paired Docker/current-code page responses and exact failing read categories. The provider failure is likely independent because its code and process/environment path did not change and it occurred before browser creation. This classification supports Docker removal as a contributor to the changed conditions, **not** a proven sole root cause of every stop.
