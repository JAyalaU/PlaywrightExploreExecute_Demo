## Boundary and Windows runtime

Keep the existing public boundary: `ProtectedContextFactory.open(ref, expected, options): Promise<ProtectedBrowserSession>`. Its returned `context`, `effectiveProfile`, `versions`, `close`/`closeWithFinalCheck`, and `onClosing` are what MCP, compiler, runner and production use. Behind the factory, make browser ownership a small backend handle (`browser`, physical presentation, runtime kind, `close`) with `docker-isolated` and `local-windows` implementations. The existing non-Docker `chromium.launch` branch and `Browser.close` path are a starting point; neither grounding nor trace/compiler/replay logic needs a rewrite. Keep RFB as a Docker-only optional capability instead of adding it to the common execution interface.

For `local-windows`, launch bundled Playwright Chromium directly with the existing restricted process environment and context options (viewport, locale, timeouts, blocked service workers, no downloads or permissions). Use a fresh browser plus context per factory `open`, so exploration, compiler, replay 1 and replay 2 retain distinct process/context/page ownership and teardown. The local view option may launch physically headed while the accepted execution profile stays headless, as the current Docker viewer does; record that distinction explicitly. A Chrome `channel` can be a later trusted opt-in after the bundled Chromium path passes, since installed Chrome version and enterprise policy add variance. No Docker daemon, Linux browser or WSL is needed for direct `chromium.launch` on Windows. On a locked-down laptop, Chromium installation and corporate process policy remain environment checks.

The operator should set a closed trusted launch value such as `PLAYWRIGHT_DEMO_BROWSER_BACKEND=local-windows`; absent value preserves Docker for the current Docker profile. The deferred route must reject backend/profile mismatches before interpretation or browser launch. Task text, model output, and request wire fields cannot select it. Add a new profile schema/version with literal `browserIsolation: 'local-windows'` (and an explicit physical-runtime view flag/metadata separate from accepted `presentationMode`); use a new profile ID/version and fingerprint. Retain v3/v4 parsing and historical artifacts unchanged. The active PoC's trusted `select` path in `admission-cli.ts` currently chooses a configured profile without validating the historical admitted-public approval, so selection and the deferred factory must agree on the same reviewed local profile. Do not change the legacy approval validators as a shortcut.

## Local frame CDP timeout ownership correction (2026-10-05)

The JPEG deadline formerly rejected the viewer's `Promise.race` while its per-attempt CDP screenshot request could remain pending; session detach ran only after that request settled. The deadline now requests idempotent Playwright CDP detach immediately and waits a bounded interval for its result before returning `CAPTURE_TIMEOUT`. A session acquired after the deadline is detached on acquisition. Late capture completion or rejection is consumed and discarded; it cannot publish a frame. Private bounded diagnostics record timeout, detach request/completion/failure or bounded wait expiry, and observable late settlement/discard, without pixels or QA fields. A stalled detach remains explicitly recorded rather than silently owned by the viewer loop. This corrects the timeout lifecycle defect; it does **not** establish the cause of the later public `body.ariaSnapshot` failure.
