# Deferred interpretation deadline hardening

This records the initial 30,000/90,000 ms hardening policy. The later authenticated live timeout led to the [60,000/150,000 ms runtime budget update](deferred-extraction-runtime-budget-update.md); that update is the current policy.

The read-only forensics of `local-bd3a4f57-411e-4572-b567-3151f956bf95` found an authenticated `interpretation / environment / EXTRACTION_DEADLINE` stop, but the stored result did not retain which of the primary, independent, or admission phases exhausted its budget. It also retained no elapsed timings or late-response metadata. The available evidence cannot distinguish provider latency from a transient environment delay for that run. No provider response or private reasoning was inspected or copied into this report.

The initial hardened interpretation policy gave each sequential semantic extraction a full 30,000 ms provider-call limit and gave the pair a 90,000 ms shared limit: 60,000 ms for the two calls plus 30,000 ms for local normalization, source validation, admission, and final handoff. The separate trusted host deadline remained 300,000 ms, leaving time for a typed stop to be authenticated and persisted. Explicit test-only limit overrides remained bounded. The primary and independent models still received separate source-first requests; there was no retry, fallback, or semantic-contract change.

A completed provider-client outcome is marked before the deferred adapter normalizes its wire shape. The per-call timer ends at that boundary; the shared timer remains active through normalization. A late completion cannot win merely because the event loop delayed a timeout callback. `providerCompletedBeforeBoundary` means the model adapter's client call settled before its allowed boundary, including a typed provider failure. It does **not** certify that an HTTP response arrived or that the extraction was structurally valid. An aborted request that later settles cannot change the recorded stop or gain admission.

The restricted timing record contains only phase, elapsed milliseconds, per-call and shared limits, remaining time, per-phase allocation, completion status, and deadline origin. It has a closed schema, carries no source, prompt, response, browser fact, or reasoning, and grants no semantic authority. On interpretation stops, it is saved as optional `interpretationTiming` inside the existing HMAC-authenticated `DeferredWorkflowPrivateAccountingV1` record. Old stop records without this field remain readable. The public ResultRecordV2, subprocess/Python contract, and stakeholder projection remain unchanged and do not contain the timing record.

Focused mocked tests covered primary and independent deadlines, a near-30-second primary with local overhead still allocating a full independent 30 seconds, successful normalization after timely provider completion, a stalled normalizer reaching the shared deadline, late completion, admission deadline, cancellation precedence, provider failure, private authenticated persistence/tampering, and public projection exclusion. At this stage the offline suites passed: deferred interpretation and deadline tests **39/39**, complete WP5A integration **21/21**, typecheck, and build. These overlap only where tests were rerun; no credentialed provider or public-target workflow ran during this hardening task. The subsequent live timeout and revised budget are recorded in the linked update.
