# P4-G2 decision: headed isolated browser and private view-only viewer

Status: **complete for P4-3 implementation**. This is an architecture decision, not a viewer implementation or a P4-3 release result. It closes P4-G2 in the [Phase 4 plan](phase-4-implementation-plan.md). P4-1 and P4-2 remain separate, completed observability capabilities.

## Existing boundary and required contract change

The current public browser is one disposable `--network none`, read-only, mountless container per `ProtectedBrowserSession`. Chromium is always started with `--headless=new`; trusted Node reaches CDP and the authoritative proxy through private Docker-exec streams, with no published container port. `ProtectedBrowserSession.close()` awaits container removal. The current isolated profile schema accepts **headless only**, and public admission v1 reconstructs a headless profile from the approved URL and DNS pins. A headed public run cannot be represented by changing only a Streamlit flag or a Chromium argument.

Add a **new `profileSchemaVersion: "4"` isolated-headed execution-profile variant** and an explicit `admissionVersion: "2"` headed public-target approval/lookup contract. The headed approval binds the same reviewed canonical target, host, port, complete DNS pins, policy, profile reference, and effective-profile fingerprint, plus the fact that headed presentation is authorized. It is created by a trusted local operator after inspection; form URL/task never create or select network or headed authority. Keep `admissionVersion: "1"` and its headless profile/lookup behavior unchanged. Admission v2 reuses the v1 inspection/DNS/policy checks but binds the headed profile, rather than making admission v1 accept a profile shape it currently rejects. The operator selects the trusted headed configuration at launch. The subprocess-v1 request still carries only the approved URL, task, and profile reference; its existing `presentationMode` and observational result fields already represent headed outcomes. No subprocess-v1 field is added.

The headed and headless profiles have distinct IDs/versions and fingerprints. Exploration and both fresh replays use the selected headed profile; each receives its own protected session/container and viewer lifecycle. A headed outcome is always `observation.state: observational`, `inputProvenance: unverified`, and `autonomousEligible: false`, including when the viewer sends no input. Existing detectable-input records remain append-only observations, never replay steps. A **separate fresh headless workflow** under its own approved profile is required for autonomous equivalence. A headed success does not certify autonomy.

## Browser and display compartment

Pin a new browser image/runtime variant with Chromium, a virtual X server, a view-only RFB server, and the static noVNC client assets needed on the trusted host. One virtual display and one Chromium process tree run inside the same container and under the same unprivileged, read-only, dropped-capability, `no-new-privileges`, disposable-storage boundary. The headed entry starts the display and view-only RFB server before Chromium, omits `--headless`, and retains the reviewed Chromium proxy and `--no-sandbox` posture. The RFB server listens only on **container loopback**. The display, RFB server, and Chromium are supervised as one protected session: failure before browser work prevents startup; loss of the display/browser after work begins follows existing browser-failure classification; viewer-service loss alone affects observation, not QA.

The container retains `--network none`, no host/repository/home mounts, no provider credential, no Docker socket, no published port, and no direct route to public, private, metadata, DNS, or host services. Browser public traffic continues solely through the existing Docker-exec proxy bridge and authoritative `ProtectedProxy`. The private CDP bridge remains separate and is never offered to a viewer. Do not fall back to a host browser or create a second browser for noVNC. Headless image/runtime behavior remains unchanged.

## Private viewer path and authorization

Use a separate `liveViewerVersion: "1"` **ephemeral viewer-lifecycle contract**, distinct from `eventStreamVersion: "1"`, `liveImageVersion: "1"`, `reportProjectionVersion: "1"`, and subprocess v1. A closed trusted launch-side `liveViewerPolicyVersion: "1"` policy with `displayApproved: true` explicitly approves local display; absence, false, or invalidity means no viewer. P4-2 capture/display approval does not grant viewer access. A P4-1 event ID is correlation, not authorization. The host may request the viewer only for an approved headed profile; task text, page content, MCP output, and Streamlit form fields cannot enable it.

Trusted Node owns the viewer gateway and the container-side RFB stream. For each protected headed session it opens a **temporary IPv4 `127.0.0.1` HTTP/WebSocket endpoint on an ephemeral port** in the trusted Node subprocess, serves only pinned local noVNC assets, and relays one authenticated WebSocket's RFB bytes through a new bounded Docker-exec standard-stream bridge to the container's loopback RFB port. No Docker `-p`, host network, public listener, reverse proxy, general API, filesystem route, CDP route, or proxy route is created. The gateway never sends browser control, provider data, or host files through RFB. The existing CDP and proxy streams remain independently owned.

The trusted Python host creates a separate per-run loopback lifecycle channel and a fresh cryptographically random **lifecycle-channel capability** before starting Node. Node receives that endpoint and capability only in the trusted child launch environment, not in subprocess request JSON, command-line arguments, browser environment, report, diagnostics, or P4-1/P4-2 channels. Node authenticates once to this lifecycle channel and sends only closed, at-most-2-KiB `ready`, `transition`, `closed`, or `unavailable` notices with the viewer's ephemeral port/path, profile fingerprint, current attempt/run owner, and applicable P4-1 stream/sequence correlation. At most 32 notices are accepted for one workflow. Python validates the notice and its established event/profile/owner correlation before making a viewer handle available to Streamlit. The lifecycle channel never carries RFB bytes, image bytes, arbitrary URL, or artifact reference. Unknown version, field, owner, or out-of-order transition makes the viewer unavailable; it cannot rewrite the final QA result.

Node generates a **distinct 256-bit WebSocket connection capability for each protected session and each permitted reconnect**. It delivers that short-lived token in a bounded, authenticated lifecycle notice; this token cannot authenticate the lifecycle channel, and the lifecycle-channel capability cannot authenticate a viewer. Streamlit embeds the pinned noVNC client for the **current** owner only. The client obtains its WebSocket token through an in-memory local UI handle and presents it in a WebSocket handshake subprotocol; no capability is placed in an HTTP request path/query, report, artifact, terminal log, or persistent Streamlit state. A URL fragment may deliver it to the pinned local client because fragments are not sent in HTTP requests; the client must remove the fragment after reading it. The pinned client/bootstrap must support this handshake without placing the token in an RFB message or URL; implementation must prove compatibility with its chosen noVNC version. The gateway checks an exact loopback `Host` and Streamlit `Origin`, the token, run/session identity, expiry, and one-active-viewer limit **before** upgrading or opening the RFB bridge. It consumes each connection capability once. A reconnect requires a fresh token sent on the same authenticated lifecycle channel while that session remains active; an old token, old session, second concurrent viewer, cross-origin request, or post-close request is denied. Responses use no-store, no-referrer, and a restrictive CSP (local pinned assets and the one same-host WebSocket endpoint only; frame ancestor limited to the loopback Streamlit origin); no general static file server or reusable media route is exposed. These checks protect this local PoC from unrelated browser origins and stale links; they do not claim isolation from malicious code running as the same Windows operator.

The gateway and **RFB server** both enforce view-only operation. The pinned noVNC client disables input, clipboard, upload, download, and UI controls, but client-side settings alone are insufficient. The gateway permits only RFB handshake and display-configuration/update-request messages toward the server; it rejects key, pointer, client cut-text/clipboard, and unknown client message types rather than blindly forwarding WebSocket bytes. The RFB server independently ignores input and disables clipboard/file-transfer extensions. Server-to-client clipboard/file data and unsupported extensions are also denied. This preserves passive viewing even if a client bypasses the Streamlit UI. NoVNC is neither a Playwright control channel nor a way to create observations that become executable steps.

## Correlation, expiry, and failure

The viewer lifecycle is scoped to **one active protected session and its attempt or replay run**. A closed P4-1 `streamId`/event sequence and validated TestSpec/profile/attempt/run IDs label that viewer; they cannot grant access. The gateway must stop serving the old container/display and revoke its capability at each exploration-to-replay or replay-to-replay transition. Streamlit must show `not_started`, `connecting`, `available`, `transitioning`, `unavailable`, or `closed` as appropriate, never relabel old pixels as the next run. It may keep the stable local viewer component mounted during one session so normal timeline refresh does not disconnect it. If the browser tab disconnects, the bounded Node workflow continues to its normal result or deadline; reconnect is allowed only with a new short-lived token for the still-active session. No viewer bytes are persisted in Python, report projection, event stream, stored evidence, or local artifacts; pixels already displayed in the operator's browser may remain in its memory until the tab closes.

Set a finite viewer lifetime no longer than the active workflow deadline and a short connection-capability expiry (at most 60 seconds); close the listener, WebSocket, RFB bridge, and container-side RFB server promptly when its session closes, on cancellation, timeout, host shutdown, or child exit. Viewer setup/authentication failure **before** browser work fails closed and disposes any created resources using existing bridge/process cleanup semantics. Once engine work has started, a viewer disconnect or RFB/gateway observation failure closes viewing and leaves Node-owned QA unchanged. A display or Chromium failure remains a real browser failure. Python's graceful cancellation path gives Node its bounded cleanup opportunity; forced process-tree termination still reports `cleanup: unverified` and requires a residual-container check. Expired or closed endpoints deny reconnection and have no residual process/listener/container.

## Implementation and release handoff

- **P4-3A — Docker expert, with security engineer:** pin the headed browser image and local noVNC assets; add the virtual display, independently view-only RFB server, loopback-only RFB listener, and supervised process lifecycle. Prove normal display of the *same* Chromium, no-mount/credential/direct-egress properties, no published port, injected RFB input denial, and forced disposal. No Node/Python/Streamlit viewer wiring in this package.
- **P4-3B — Node specialist, with Python host integrator for the closed lifecycle exchange:** add the new versioned headed profile and trusted admission/approval variant, trusted viewer policy, private Docker-exec RFB bridge, temporary authenticated gateway, and correlated per-session lifecycle notices. Keep admission v1, subprocess v1, report projection v1, and headless behavior unchanged. Prove normal owner transitions, wrong/stale capability/origin/profile denial, proxy-only public traffic, failure/timeout/cancellation disposal, and headed observational classification. If the admission and gateway seams cannot be independently bounded, stop for architecture/security review.
- **P4-3C — Python frontend developer with test automator/security reviewer:** validate the separate lifecycle notices; embed the pinned view-only client without granting browser authority; show truthful transition/closed states beside P4-1 and P4-2. Run exact-profile protected runtime, denial, and residual-resource tests, a human-operated real-provider headed UI proof, and a separate fresh headless proof of autonomous equivalence. A skipped Docker case or mocked provider does not close the live gate.

Release must validate one normal headed public run, one failed/denied viewer path, and one cross-process Streamlit/Node/browser transition. It must also prove browser file/credential isolation, proxy-only egress, no input/clipboard/file transfer even with a forged client, exact loopback binding and origin/capability checks, no endpoint after expiry/cancel/failure, no residual container, profile/fingerprint correctness, unchanged final QA and two fresh replays, and separate headless autonomous eligibility. The actual noVNC asset and RFB-server behavior, Docker Desktop lifecycle, and Streamlit iframe stability require runtime proof; they are **not** established by this decision document. A failure of any isolation or input-denial proof blocks P4-3 rather than relaxing the boundary.
