# Phase C Docker retirement preflight (post-B5)

Date: 2026-10-06. Scope: current checked-out TypeScript, Python, config, scripts, tests, and `infra/public-browser/` after B5. This is a source-reachability audit and implementation plan. No runtime, Docker, provider, public-site, or browser-cohort proof was performed. The old artifact generations have no supported readback requirement. Historical architecture documents are not execution authority.

Historical experiment reports remain for Phase D.

`PLAYWRIGHT_DEMO_BROWSER_BACKEND` no longer selects a backend. A nonempty value, including the old `local-windows` spelling, is rejected as stale trusted configuration by both Node and Python. Schema-3/4 trusted config is rejected by the strict native parser. Direct Node approval checking from C1 remains mandatory before browser creation. Offline validation passed: typecheck and fresh build; default `npm test` 180/180 including native approval rejection and two-run `QA_ASSERTION_PASSED` with cleanup; frame/cancellation 15/15; bounded Python 32/32; and the focused schema-3/4 rejection and local navigation-timeout extension 6/6. Nine source-less compiled JavaScript files were removed; fresh build leaves zero orphans. No provider, public target, or Docker process was invoked. The earlier source analysis below is a **pre-C1/pre-C2 snapshot**, not current executable reachability.

## Decision and highest-risk findings

**Recommendation: two checkpoints, C1 then C2.** C1 narrows the native profile/admission contract and separates the local frame channel from RFB, preserving the exact native schema-5 serialized profile and fingerprint. C2 removes Docker execution, schema-3/4 and old approval/config support, RFB/noVNC, infrastructure, and exclusive tests. The split makes profile/approval and live-view regressions observable before deleting the alternative backend. Cost: one extra checkpoint and small import migrations; gain: a reversible boundary and a simpler C2 deletion.

The product does **not** require Docker. The ordinary Python UI and Node CLI require native schema 5 and reject a Docker selector ([Python route](../../../src/playwright_demo/ui_workflow.py), [Node route](../../../app/local/agentic-workflow.ts), [admission `select`](../../../app/profile/admission-cli.ts)). However, `ProtectedContextFactory` still imports `IsolatedBrowser`, and its direct-call default is `docker-isolated` when `PLAYWRIGHT_DEMO_BROWSER_BACKEND` is unset ([context.ts:40-47,125-170](../../../app/profile/context.ts)). Product composition passes `'local-windows'` explicitly ([semantic-general-workflow.ts:132-161](../../../app/local/semantic-general-workflow.ts)); experiments and tests can still instantiate the generic factory directly. A grounding stability experiment actually calls the old parser and creates schema 3 when the variable is unset ([semantic-grounding-v1-stability-experiment.mjs:136-151](../../../scripts/semantic-grounding-v1-stability-experiment.mjs)). That is an experiment stale-default hazard, not product fallback.

The local browser has no enforced Docker network policy. Native schema 5 forbids `networkPolicyRef`, but trusted config still accepts `networkPolicies`, and `ProfileCatalog.resolve` synthesizes `legacy-unused-policy` for schema 5 ([contracts.ts:56-65,111-156](../../../app/profile/contracts.ts), [local/contracts.ts:62-79](../../../app/local/contracts.ts)). Native approval's URL, reviewed DNS address set, profile ref and fingerprint are trusted **admission metadata** ([admission.ts:264-332](../../../app/profile/admission.ts)); the local Chromium launch has no proxy/egress pin ([context.ts:165-201](../../../app/profile/context.ts)). Do not describe DNS pins as local runtime isolation. Keep exact target approval; remove unused policy metadata in C1/C2.

**C1 security prerequisite, confirmed from direct-call source:** Python's ordinary UI calls admission `select`, which requires an approved target ([ui_workflow.py:110-129](../../../src/playwright_demo/ui_workflow.py), [admission-cli.ts:46-61](../../../app/profile/admission-cli.ts)). Direct Node v2 CLI does not call `select`: its local workflow only compares target URL *if* an approval exists, and native selection accepts a sole schema-5 profile with no approval ([agentic-entry.ts:17-24](../../../app/subprocess/agentic-entry.ts), [agentic-workflow.ts:19-35](../../../app/local/agentic-workflow.ts), [local/contracts.ts:127-135](../../../app/local/contracts.ts)). The factory stores `externalTargetGate` but never invokes `authorize` ([context.ts:125-140](../../../app/profile/context.ts)). Therefore direct Node execution can apparently use a schema-5 config without `publicTargetApproval`. C1 must require and validate native approval in the production Node workflow before browser creation, while keeping an explicit test-only offline fixture seam; add a direct-CLI absent/mismatched-approval negative test. This is independent of Docker deletion and must not be mistaken for the UI path's existing protection. Runtime exploitability was not exercised in this read-only audit.

## 2. Schema-5 independence and remaining profile coupling

`LocalWindowsExecutionProfileSchema` is constructible from its own strict fields: `id`, `version`, Chromium, viewport/locale/device options, timeout policy, optional `authStateRef`, `profileSchemaVersion:'5'`, `presentationMode`, `browserIsolation:'local-windows'`, and `browserRuntime:'playwright-chromium-windows'`. It forbids `networkPolicyRef` ([contracts.ts:9-29,56-65](../../../app/profile/contracts.ts)). `approveLocalWindowsPublicInspection` and headed counterpart build it directly and calculate its `ProfileCatalog` fingerprint without schema-3/4 or a policy ([admission.ts:250-312](../../../app/profile/admission.ts)). `selectNativeLocalWindowsProductProfile` requires an existing schema-5 member and does not take the Docker conversion branch ([local/contracts.ts:109-168](../../../app/local/contracts.ts)). Native selection is therefore independent of Docker image, container, proxy and RFB identities.

**Remaining transitive shape coupling:** `ExecutionProfileSchema` still unions legacy/unversioned, v2, v3, v4, v5; `EffectiveProfile` always carries a synthetic `policy`; fingerprinting strips `networkPolicyRef` and ignores policy for *all* profiles ([contracts.ts:67-73,111-156](../../../app/profile/contracts.ts)). Native fingerprint is SHA-256 of JSON serialized native runtime profile, not Docker-derived fingerprint. C1 should retain that byte-level canonical behavior so existing native approvals remain valid. `parseActivePocTrustedConfiguration` leaves schema 5 unchanged but rewrites old profiles' navigation timeout ([local/contracts.ts:82-97](../../../app/local/contracts.ts)). Its old-profile rewrite can disappear after schema 5 is the only accepted profile. Historical fingerprints/artifacts need no supported readback; old approved Docker config cannot be silently reclassified as schema 5.

| Contract/field | Phase C decision |
|---|---|
| Schema 5 profile fields and `browserIsolation:'local-windows'`, `browserRuntime` | `KEEP_SCHEMA5`; preserve identity and fingerprint. |
| Schema 3/4, unversioned/v2 profile unions, Docker `browserIsolation`, Docker-source transform | `DELETE_IN_C`; reject old config clearly. |
| `networkPolicyRef`, `NetworkPolicySchema`, `EffectiveProfile.policy`, catalog policy map and `networkPolicies` | `DELETE_IN_C` after native catalog callers are narrowed; local browser does not enforce them. Preserve approval `addresses`/inspection digest independently. |

| `presentationMode`, `liveViewerPolicy`, `evidencePolicy`, `artifactRoot`, `retentionDays` | `KEEP_SCHEMA5`; presentation and evidence policy remain trusted config, artifacts/stores use root. |

## 4. Admission and network-policy migration

Native `admission-cli select` reads bounded trusted JSON, requires schema 5, validates exact approved target, reference and fingerprint, and emits the bounded v1 selection response for Python ([admission-cli.ts:12-62](../../../app/profile/admission-cli.ts), [public_admission.py:31-65,68-134](../../../src/playwright_demo/public_admission.py)). Keep `select`, `inspect`, native headless/headed `approve`, `canonicalPublicUrl`, public-address rejection, DNS inspection/fresh comparison, and native approval validation. `lookup` is a separate compatibility exchange: it accepts old schema/profile unions and approval types ([admission-cli.ts:64-85](../../../app/profile/admission-cli.ts)); Python product uses `selection_only=True`. Remove old `lookup` if no retained caller remains, or narrow it to schema 5 only if a current operator/tool caller is identified. Remove schema-3/4 admission constructors ([admission.ts:165-248](../../../app/profile/admission.ts)), legacy profile-match/fingerprint branches ([335-389](../../../app/profile/admission.ts)), and hardcoded named-site approval variants ([public-target.ts:10-25,53-94](../../../app/profile/public-target.ts)). Keep native approval `targetUrl`, `host`, `port`, `addresses`, `inspectionDigest`, `executionProfileRef`, `profileFingerprint`, `approvedAt`, and headed `presentationMode`; these are approval provenance, not network enforcement.

**Network policy recommendation:** remove unused `networkPolicies` and `networkPolicyRef` from native trusted config/catalog and delete `app/profile/network.ts` after policy-only tests. Its `ProtectedProxy`/DNS pinning has no product caller ([network.ts:27-46,84-99](../../../app/profile/network.ts)); the local Chromium branch launches without it. Keep the reviewed DNS addresses and digest in the approval contract, named as inspection/approval evidence. Do not claim they constrain subsequent browser requests, DNS resolution, redirects or third-party requests. This reduces false security claims and stale config burden without designing a new network subsystem. If product policy requires runtime egress restriction, that is a separate security decision and cannot be satisfied by retaining inert metadata.

The surviving Docker `IsolatedBrowser.open` also currently uses `docker run --network bridge` and does not import `ProtectedProxy` ([isolated-browser.ts:160-182](../../../app/profile/isolated-browser.ts)); old `infra/public-browser/README.md` text about mandatory proxy/networkless launch is therefore historical and should not be treated as evidence of enforcement. The network policy code is test/barrel reachability, not a hidden active product safeguard.

Current trusted config accepts `profiles` (any union member), `networkPolicies` default `[]`, `evidencePolicy`, optional `liveImagePolicy`/`liveViewerPolicy`, `artifactRoot`, `retentionDays`, optional `publicTargetApproval` ([local/contracts.ts:62-79](../../../app/local/contracts.ts)). The CLI writes native schema 5, `networkPolicies:[]`, native approval and the evidence/artifact/retention values; headed approval adds `liveViewerPolicy` ([admission-cli.ts:91-124](../../../app/profile/admission-cli.ts)). Target production config is the **same native profile and approval object** with `networkPolicies` omitted, schema-5-only `profiles`, and approval required at the direct Node boundary. Keep `evidencePolicy`, `retentionDays` and optional viewer policy fields during C to avoid unrelated config churn; source search finds them parsed/constructed but no product runtime reader outside `local/contracts.ts`/`admission-cli.ts`, so their longer-term disposition belongs to E or a separate policy review. `liveImagePolicy` likewise has no current runtime reader. The existing native config remains valid if C accepts and ignores its empty `networkPolicies:[]` during one migration checkpoint; strict final schema would require removing that empty field. The four checked-in `config/public-*.json` files still contain Docker schema 3 and policy data ([config/](../../../config/README.md)); none is an active native product config. Archive them as historical fixtures or replace through fresh operator approval. No fingerprint rebadging or automatic conversion.
