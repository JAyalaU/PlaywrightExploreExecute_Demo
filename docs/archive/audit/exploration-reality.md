# Exploration reality audit

Scope: the current `structured-action-v1` TestSpec v5 path through M7, protected MCP, current-state binding, trusted observations, and trace v4 assembly. The `goal-directed-v1` route shares the action and verification controllers but uses TestSpec v4 and trace v3. The released `agentic-exploration-v1` controller is a separate older route without VerificationGoals. This is a code audit, not a live-provider proof. Sources: `app/interpretation/agentic-goal-controller.ts`, `verification-strategy.ts`, `app/exploration/{mcp,current-state,trusted-observation,trace-assembly-v4}.ts`, and the contracts in `app/domain/{action-target-intent,action-identity-witness,observation-contracts,verification-comparison}.ts`.

## What M7 actually controls

The action model receives one validated authored step, the current URL, a bounded protected-browser snapshot (16,384 model-facing characters), candidate and prerequisite counters, an optional `browser_find` result, and, after an action, only `state_changed` or `state_unchanged`. It returns one strict decision v3: `inspect` (optional semantic text focus), `act` (snapshot ref, click/fill/select_option, authored or discovered prerequisite, expected state change), `observe_target` (for older authored targeted assertions), `evaluate` (achieved/alternative/inspect/unresolved), or `stop`. It cannot submit selectors, coordinates, scripts, arbitrary MCP calls, an action value, or an identity witness. The runtime supplies fill/select values from TestSpec. In the current v5 route, authored non-navigation steps are actions or VerificationGoals; the older assertion/wait handling remains in the shared controller for older schemas. See `AgenticDecisionV3Schema`, instruction, and step loop in `agentic-goal-controller.ts`.

The separate verification model receives a VerificationGoal, current trusted observation records, up to eight prior records, and an action ordinal. It chooses a strict v4 `observe` request or `conclude` with an observation-ID comparison. It can iterate over observed results, but the controller independently checks that the comparison means the authored goal, that current evidence is runtime-owned and fresh, and that its claimed satisfied/unsatisfied conclusion agrees with the facts. Unsupported and unresolved end exploration without a QA verdict. See `verification-strategy.ts`.

| Primitive / question | Model choice | Trusted/runtime facts and fixed policy | Limit |
|---|---|---|---|
| Navigate | Interpretation fixes the URL; M7 does not choose a new destination. | MCP `browser_navigate` checks approved address/policy; runtime captures a new snapshot. | No free navigation or policy change. |
| Inspect snapshot / find | Action model chooses `inspect` and optional find text. | MCP `browser_snapshot` and `browser_find`; current-state owner hashes full snapshot and URL. | Snapshot text is untrusted and may be truncated for the model. Find is only a text aid, not evidence. |
| Select target and act | Model chooses a currently shown `ref`, action kind, source and prerequisite reason. | `CurrentStateExploration.bind()` proves ref, page/frame/snapshot, role, visibility, enabled state, operation compatibility, scope and (v5 authored actions) exact intent identity; `act()` repeats proof and invokes MCP click/fill/select. | The value is fixed by TestSpec; v5 exact accessible name and uniqueness must already be available. |
| Observe consequences / reconsider | Model judges after a fresh observation. | Runtime computes state digest and labels change/unchanged. Two authored candidates per goal, six prerequisites, 40 actions, 60 decisions, 80 snapshots, two recoveries and 120 seconds bound the loop. | Changed-state recovery must replay a known prefix in a fresh session; after any successful verification strategy it stops rather than transplanting evidence. |

The MCP adapter advertises and requires `browser_navigate`, `browser_snapshot`, `browser_find`, `browser_generate_locator`, `browser_click`, `browser_fill_form`, `browser_select_option`, and `browser_wait_for` (`mcp.ts`). M7's current decision surface actually reaches navigate, snapshot, find, click, fill and select through controller/runtime calls. `generateLocator` has an adapter method but is not called by this M7 controller. `waitForText` is exposed in the session port but is not called by the current goal-directed loop. The separate trusted observation API uses fixed Playwright reads and semantic locators behind the runtime; it is not a general MCP/Playwright command channel for the model.

## Identity, state and scope

An action starts from a snapshot ref, which must occur once in the current full snapshot and resolve to exactly one actual frame node. The binding records session, page, frame, snapshot epoch/digest, originating step, operation, selected role/name, and justification; it expires after ten seconds and is invalidated by a new observation or changed page. `act()` rechecks the full MCP snapshot, current page/URL, actionability and requested value immediately before use. A failed bind/action is exploratory resolution, never QA failure (`current-state.ts`).

For an authored v5 action, `ActionTargetIntentV1` is already in TestSpec. The selected node must have its exact nonempty accessible name. Explicit role must be eligible; an unspecified role searches all eligible roles and requires exactly one total exact-name match: click = button/link/checkbox/menuitem/radio/option, fill = textbox, select_option = combobox. The count includes hidden matches, while the selected action must be visible and enabled; fill must be editable and select must be a native `<select>`. The runtime records `ActionIdentityWitnessV1` before acting and repeats the unique semantic role/name/ref proof at action time. The model supplies only the ref. See `#proveActionIntent()` and `bind()/act()` in `current-state.ts` and `action-target-intent.ts`.

Scopes for action identity are a bounded ordered list of exact named menu/dialog/region, a unique row containing an exact named cell, and frame hints. A nested action frame must have unique, durable title or data-testid ownership anchors; authored v5 frame hints currently match exact **titles**, so a frame identifiable only by test ID cannot satisfy such an authored hint. Verification semantic queries support a main or nested frame (title or test ID), a role, optional exact name, and up to four exact scopes of dialog/menu/region or row-with-named-cell. Runtime must resolve each scope uniquely. `TrustedObservationSessionV1` hashes frame DOM and ARIA snapshots, page/profile/current-state owner and navigation/mutation epochs before and after reads. `currentEvidence()` accepts only its own still-current complete record, not a model-made, stale, error or snapshot record (`trusted-observation.ts`).

Prerequisites are model-selected clicks on visible, enabled controls, marked `expose_target` or `reach_state`. They are separately bound and cannot complete the authored action. The controller further requires a nonempty prerequisite accessible name literally present in the authored step text, target description or scope description. This is a significant hard-coded discovery limit: a useful unlabeled menu opener or a control whose label is only implied by context cannot be used as a prerequisite. A passive state transition can be recorded only with an already authored, satisfied wait/visibility/URL condition and protected witness. These constraints are in `agentic-goal-controller.ts` and `current-state.ts`.

## Eight capability answers

1. **Unfamiliar control:** M7 can inspect snapshots, search text, try bounded current refs, and observe consequences for the three approved actions. It cannot infer and execute a new operation or query arbitrary DOM/control metadata. A custom dropdown is outside `select_option` actionability because `act()` requires native `<select>`.
2. **Role only:** Verification can count by role without a name and read a property if that query has one match. Authored v5 action identity cannot use role only: `ActionTargetIntentV1.accessibleName` is mandatory and nonempty.
3. **Unique unnamed control:** A role-only verification query can establish that one unnamed control exists and read supported properties. An authored v5 click/fill/select cannot bind it, even if the snapshot ref is unique, because the exact nonempty-name intent cannot be formed/proven. A discovered prerequisite also requires a nonempty label in authored text.
4. **Relationships/context:** M7 can compose reviewed frame/scope ancestry and row-with-cell context, then count or inspect a role/name within it. It cannot express general sibling, adjacency, visual position, label association, option-parent, or relative-to-another-target predicates.
5. **Select/option relationships:** It can see what the ARIA snapshot exposes and separately count `option` roles or read explicit `aria-selected` on one option; it can read the native combobox value. There is no reviewed observation primitive linking an option to a particular select or enumerating native option values. Snapshot inspection is not evidence-grade.
6. **`Option 1` as argument:** M7 can operate with `Option 1` as the already validated `select_option.value`; it cannot move a phrase from target identity into the argument after interpretation. The action decision contains a ref and action kind, no value field; runtime reads TestSpec's value.
7. **Arbitrary semantic combinations:** The verification model can choose combinations permitted by `SemanticObservationQueryV1` (reviewed role, optional exact name, exact frame and bounded scopes) and reviewed comparisons. It cannot query arbitrary combinations outside that grammar, join two queries into a relationship, inspect general attributes, or use selectors/DOM evaluation.
8. **Pre-M7 hard coding:** Workflow/TestSpec version, ordered steps, operation and argument, v5 exact target name/role policy/scope, URL, VerificationGoal intent/subject, allowed tools, native-select requirement, actionability, budgets, prerequisite label rule, proof freshness and comparison vocabulary are fixed before or around M7. The model chooses a candidate ref and verification strategy within them.

## Case studies

**Add/Remove Elements.** In the structured route, a validated named link action can be selected from a snapshot; the runtime proves the exact `link`/`Add/Remove Elements` intent is unique before clicking. A named `Add Element` button follows the same path. The verification model can ask for a complete zero count of `Delete` buttons before the click, a fresh positive count afterward, and an exact later count. The runtime owns those counts and their epochs, while the model chooses the observation requests and comparisons. The protected-fixture end-to-end Add/Remove path is documented in `docs/current-status.md` and exercised by `tests/structured-action-identity-wp4b.spec.ts`; the structured route still lacks completed real-provider public-target proof. A successful M7 strategy alone does not establish replay or QA.

**Dropdown / `Select Option 1`.** The MCP adapter and current-state runtime can execute `browser_select_option` on a selected, visible, enabled native `<select>` whose ref is current, with the value supplied by TestSpec. The verification API can count `combobox`/`option` roles and inspect one combobox `value`, but cannot attest which option belongs to which dropdown or that a displayed option maps to the operation value. Under v5, the authored action first needs a separate exact nonempty accessible name for the **control**, plus `select_option` as operation and `Option 1` as its **argument**. If the request only says `Select Option 1`, the phrase identifies an option/argument, not necessarily the dropdown; an unnamed control has no representable v5 action intent. A named dropdown can be represented if its name is authored and unique in its scope/frame, and its option value is separately available. Runtime uniqueness cannot compensate for an unrepresentable or misassigned interpretation target. The repository does not contain a completed structured dropdown provider trace, so this is a contract-path analysis, not a claimed observed stop.

### Exploration capability boundary

M7 can compose bounded snapshot inspection, current-ref selection, three reviewed actions, exact role/name/scope/frame semantic reads, property reads and closed comparisons to solve tasks whose target identity, operation and argument already fit TestSpec v5 and whose verification reduces to those observations. It cannot discover or prove an unnamed authored action target, execute non-native select semantics, express an option-to-control or general spatial relationship, or revise a preassigned target/argument boundary. Those cases require a new primitive or an earlier contract change; they cannot be solved by more M7 decisions over the present tools.
