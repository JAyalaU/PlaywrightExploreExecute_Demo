# Interpretation reality

Scope: the model-facing interpretation call, its provider wire, normalization, and TestSpec validation. This is a code audit, not evidence of real-provider interpretation quality. No browser or provider workflow was run.

## Selected routes and model input

The trusted local v2 workflow selects `agentic-exploration-v1` by default, `goal-directed-v1`, or `structured-action-v1`; the request does not choose this version. `app/subprocess/agentic-cli.ts` reads the trusted environment selection and `app/local/agentic-workflow.ts` chooses the adapter and `interpretTask` mode. The separate legacy v1 local handoff uses `createOpenAIModelAdapters` and the `qa_interpretation_v1` format (`app/local/workflow.ts`, `app/interpretation/openai-adapters.ts`).

| Workflow | Interpretation adapter and provider format | Accepted TestSpec | Interpretation prompt |
|---|---|---|---|
| Legacy v1 handoff | `createOpenAIModelAdapters`, `qa_interpretation_v1` | v2, or v3 for the exact link-collection assertion | `INTERPRETATION_SYSTEM_INSTRUCTION` |
| `agentic-exploration-v1` | `createOpenAIAgenticInterpretationModel`, `qa_agentic_interpretation_v2` | v2/v3; `verification_goal` is rejected by this route | Legacy interpretation prompt |
| `goal-directed-v1` | Same agentic v2 adapter/format | v4 | `AGENTIC_INTERPRETATION_SYSTEM_INSTRUCTION` |
| `structured-action-v1` | `createOpenAIStructuredActionInterpretationModel`, `qa_structured_action_interpretation_v3` | v5 | `STRUCTURED_ACTION_INTERPRETATION_SYSTEM_INSTRUCTION` |

The agentic format contains a `verification_goal` variant even when `agentic-exploration-v1` selects it. The `interpretTask` mode rejects that variant for the older route. Conversely, v5's format contains only navigate, click, fill, select, and verification goals. The current code has wired v5 through production (`app/local/agentic-workflow.ts`); the opening sentence in `docs/structured-action-identity-wp1.md` still calls it an unrouted opt-in contract and is stale. `docs/system-overview.md` mainly describes the released v2/v6 baseline and its version map does not cover the later v5/v4/v8 candidate; `docs/current-status.md` identifies that candidate and its pending live gate.

The interpretation request gives the model the entire user instruction and a system instruction, with no page snapshot, browser tool, profile details, or trusted approval authority (`app/interpretation/interpret.ts`). The Responses transport sends a strict JSON schema, `tools: []`, `tool_choice: 'none'`, no conversation storage, and bounded input/output (`app/interpretation/openai-responses.ts`). The provider must return a single envelope with `response` equal to `test_spec`, `ambiguous`, or `unsupported`; a successful `test_spec` has ordered steps. The adapter validates and normalizes the wire before `interpretTask` validates it again. The model does not supply the TestSpec ID, schema version, execution profile, or start state; trusted code attaches those.

## Reasoning delegated to interpretation

The model segments the request into ordered authored clauses, chooses a closed action type, assigns step IDs, maps navigation to an absolute HTTP(S) URL, separates action targets from fill/select values, and preserves verification clauses and polarity. The goal-directed prompt specifically asks it to retain a locator sentence and adjacent “Confirm it exists” as one verification goal. It can omit uncertain optional verification subject or intent hints. Verification strategy and deterministic assertion choice are deferred to M7; a new verification request need not name an assertion type (`app/interpretation/interpret.ts`, `app/domain/verification-goal.ts`).

V5 adds a materially earlier decision: for each authored click/fill/select, interpretation must settle the operation, exact authored accessible name, explicit role if the clause states one, and any authored ordered semantic scope. The prompt says not to defer these language decisions to exploration or compilation. It may leave the **role** unspecified, but not the **accessible name**. It cannot return a goal such as “operate the control associated with Option 1” as an authored action without reducing it to the v5 target and argument structure (`app/interpretation/interpret.ts`, `app/domain/action-target-intent.ts`).

## Actual authored structures

`app/domain/schema.ts` defines the closed `AuthoredStepSchema` and `TestSpecSchema`; `app/interpretation/openai-wire.ts` defines the provider formats. The common `Target` is `{description, scope?}` where scope is an ordered array of menu/dialog/region/row/frame descriptions. It is semantic text, not a selector or a browser observation. V5 additionally requires `actionTargetIntent` on each click/fill/select and forbids it on other versions. V5 accepts only navigate, click, fill, select, and verification goals; it excludes the legacy assertion and wait variants.

| Step | Model must return | What is decided before browsing |
|---|---|---|
| `navigate` | `id`, authored `sourceText`, absolute HTTP(S) `url` | Destination URL. No target intent. |
| `click` | `id`, `sourceText`, `target`; in v5, `actionTargetIntent` | Action operation and target identity. |
| `fill` | Same target fields plus literal/dataRef `value` | Input value separately from target identity. |
| `select_option` | Same target fields plus literal/dataRef `value` | The option/value as operation argument separately from the select control. The format has no separate option-target identity. |
| `verification_goal` (v4/v5) | `id`, verbatim `sourceText` and `instruction`; optional `subject`, `intent`, `dependsOnStepId` | Authored verification meaning; the strategy/assertion is deferred. |

`VerificationGoal.subject` can optionally contain role (`button`, `link`, `dialog`, `row`, `textbox`, `checkbox`, `heading`), accessible name, and one to four ordered scopes. `intent` is optional and, if present, is one closed hint: presence (present/absent), property (visible/enabled/checked boolean), cardinality (equal/at_least/at_most and count), relationship (above/below/before/after and other text), or temporal (appears/disappears). This is the main natural-language opening before exploration: the exact verification instruction survives even when no intent or subject hint fits. It is not an unrestricted verification contract; the clause must be authored and recognizable as verification (`app/domain/verification-goal.ts`).

`ActionTargetIntentV1` is a strict object: version `1`, matching `sourceStepId`, matching `operation` (`click`, `fill`, `select_option`), role as an explicit reviewed role **or** `{kind:'unspecified'}`, nonempty exact `accessibleName`, `exact:true`, unique name source span, and optional one to four ordered scope entries each with a source span. Explicit roles are limited to button/link/textbox/checkbox/combobox/option/menuitem/radio. The role eligibility used downstream is narrower by operation: click button/link/checkbox/menuitem/radio/option; fill textbox; select combobox (`app/domain/action-target-intent.ts`). The provider sends `nameSourceText` and role/scope `sourceText` fragments. Normalization finds unique half-open UTF-16 spans in the action clause; the model does not directly choose numeric offsets (`app/interpretation/openai-wire.ts`).

The accessible name is mandatory even with unspecified role. `target.description` must equal that name exactly and `target.scope` must equal the intent scope. An explicitly authored role may not be omitted as unspecified; an unmentioned role may not be inferred from a page that interpretation cannot see. Source spans locate authored text, not browser facts. One action has one target intent; it does not describe a collection of possible controls. A verification goal can express cardinality, whereas a v5 action cannot leave its target as a collection or an unnamed contextual relationship (`app/domain/action-target-intent.ts`, `app/domain/schema.ts`).

## Validation and rejection boundary

Provider output passes the Responses envelope checks, strict wire parser, normalization, the internal `responseSchema`, `sourceText` inclusion in the full instruction, `TestSpecSchema`, unique step IDs, and per-step fidelity (`app/interpretation/openai-responses.ts`, `openai-wire.ts`, `interpret.ts`, `app/domain/validate.ts`). Unknown fields and selector/code-like semantic text are rejected. Navigation URLs are bounded to absolute HTTP(S) without credentials. For v5 actions, fidelity checks exact step/operation linkage, a unique verbatim name span, target/name equality, contrast or negation outside the name, explicit role grounding, operation cues, operation contradictions, and scope/frame grounding. These are mechanical safeguards; they do not prove arbitrary English interpretation. For verification goals it checks authored clause and identical instruction, previous-step dependency, verification cue, standalone pronoun ambiguity, grounded optional role/name/scope hints, polarity, counts, relationships, and temporal preservation (`app/domain/action-target-intent.ts`, `verification-goal.ts`).

Model `ambiguous` becomes `AMBIGUOUS_INSTRUCTION / MATERIAL_AMBIGUITY`; model `unsupported` becomes `INTERPRETATION_FAILED / UNSUPPORTED_REQUEST`. Invalid structured v5 action or verification-goal fidelity becomes material ambiguity. Other TestSpec validation becomes `INTERPRETATION_FAILED / INVALID_TEST_SPEC`. Malformed/oversized model output, bad normalization, provider refusal/incomplete/error/timeout, and invalid request have typed interpretation or provider failure paths. The local v2 boundary maps provider/model stops to **environment**, not QA, and exposes only bounded safe terminal reasons (`app/interpretation/interpret.ts`, `app/local/agentic-workflow.ts`). The explicit v5 action identity is checked before any browser session is opened.

## Concrete request readings

| Clause/case | What the current interpretation contract can represent |
|---|---|
| “Click the Add/Remove Elements link.” | V5 click with exact name `Add/Remove Elements`, explicit role `link`, and authored name/role spans. This is exercised with injected model output in `tests/structured-action-identity-wp1.spec.ts`. |
| “Click on Add/Remove Elements.” | V5 click with the same exact name and `role.kind='unspecified'`; the downstream runtime must prove a unique eligible selected control. The six paraphrase fixture covers this shape, not independent real-model phrasing quality. |
| “Select Option 1.” | The phrase gives an option argument but does not name the select **control**. A v5 `select_option` still requires a nonempty exact target accessible name and a separate `value`; setting target name to `Option 1` would conflate argument and control unless the control truly has that authored name. The model can return ambiguity; the requested select action cannot be faithfully encoded from this clause alone. A click interpretation of the option would be a different operation and depends on semantics absent from this text. |
| Unnamed dropdown | `select_option` requires an exact nonempty authored accessible name for the combobox target. A unique unnamed control, even if discoverable in the browser, has no faithful v5 action identity from an unnamed clause. |
| Named dropdown | If the clause names the control and separately names the desired option/value, v5 can encode `target.description = actionTargetIntent.accessibleName = control name` and `value = option/value`; explicit `combobox` role is possible only if authored. Runtime matching remains a separate question. |
| Button with no useful accessible name | An authored description such as position or relationship does not substitute for the required exact accessible name. Optional scope cannot replace it. If the button is genuinely unnamed, v5 cannot represent it as an authored click target. |

The Add/Remove interpretation regression and end-to-end fixtures inject already structured model output; they establish schema, normalization, fidelity and downstream wiring, not that the live interpreter reliably chooses the structure (`tests/structured-action-identity-wp1.spec.ts`, `tests/structured-action-identity-wp4b.spec.ts`). The current status records a structured live attempt that stopped in interpretation before storing a TestSpec, and a subsequent adapter-selection correction with mocked transport; it does not report completed structured live proof.

### Interpretation capability boundary

The LLM may reason freely about clause segmentation, action/verification meaning, verification prose and optional hints, and mapping authored phrases to the closed operations. For v5 authored actions, it must reduce the request to **navigate or a single click/fill/select operation with an exact nonempty authored accessible name, a grounded optional role and scope, a separate fill/select argument, and unique source provenance** before exploration. Requests outside that structure currently cannot reach exploration as faithful v5 authored actions; verification goals preserve more prose for later strategy choice.
