# P2-1 implementation plan: real model adapters

## Purpose and boundaries

P2-1 connects the existing M7 interpretation and step-decision interfaces to the OpenAI Responses API. The approved [architecture](architecture.md), [TestSpec contract](test-spec-schema.md), [Phase 2 roadmap](phase-2-roadmap.md), and [integration decisions](phase-2-integration-decisions.md) govern this work. The model returns data to the existing validators and bounded resolver; accepted `ResolvedTestSpec` data alone drives replay.

Use `gpt-5.6-terra` and reasoning effort `medium` by default, with both configurable independently of the adapter contracts. Provider credentials stay outside TestSpecs, resolved specs, and normal evidence. Requests use Structured Outputs and `store: false` where supported. The provider receives the whole task only for interpretation, and only the existing bounded `StepDecisionContext` for each decision. It receives no Playwright, MCP, browser, or runner tool handles.

Current integration points are `InterpretationModel.complete` in `app/interpretation/interpret.ts`, `StepDecisionModel.complete` and `createStepDecision` in `app/interpretation/orchestrate.ts`, and `handoffTask` in `app/interpretation/handoff.ts`. M7 already owns call limits, deadlines, local parsing, semantic validation, ref checks, and typed handoff. Keep those controls authoritative. `app/exploration/resolve.ts` persists step-decision errors as exploration reasons, so provider errors crossing that boundary must contain stable, sanitized codes rather than raw SDK or HTTP messages.

The [OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs) requires a root object and required fields in strict schemas. The existing interpretation and decision responses are closed discriminated unions, and some nested TestSpec fields are optional. The provider wire schema therefore needs a narrow, tested representation that maps deterministically to those *existing* closed responses. Structured Outputs does not replace local validation. The [model reference](https://developers.openai.com/api/docs/models/gpt-5.6-terra) lists Responses and Structured Outputs support for the selected model.

**Dependency order:** A → B → C → D. Each package can be handed to a fresh `ai-engineer` session using this plan, the approved docs, and current repository state. Fixture preparation and review of permitted input fields can proceed alongside A/B, but production adapter wiring waits for the wire and transport contracts. Keep provider-specific code under the existing interpretation ownership boundary or a small adjacent module within the same Node package; no new service is needed.

## Contract and failure gates

- **Input:** Interpretation transmits the validated request's task text and existing system instruction. Step decisions transmit exactly M7's bounded context: authored step, limited prior statuses, current URL, bounded snapshot/find excerpt, prerequisite count, and alternative-attempt flag. The provider cannot select a new profile, network policy, TestSpec operation, MCP tool, or runner action.
- **Output:** Accept only one completed, non-refusal structured response for the requested stage. Normalize the provider wire representation without guessing missing semantics, then let M7's closed schemas and TestSpec validation accept or reject it. Unexpected extra fields, an unsupported operation/decision, and an output that cannot map exactly are failures. Do not treat a provider-side schema guarantee as proof of semantic correctness.
- **Failure:** Preserve existing typed categories: interpretation rejects malformed/unsupported output and reports provider/timeout failures; step-decision errors become typed MCP exploration failures with sanitized stable reasons. No failure may fall back to selector guessing, arbitrary tool use, a different model response contract, or silent regeneration. Provider refusals and incomplete responses are explicit failures, never empty successful objects.
- **Bounds and evidence:** Honor M7's abort signal, response-size limit, one whole-task call, per-step decision count, and retry limit. Restrict SDK retries or align them with those limits. Record only safe provider decision metadata needed to diagnose model/configuration and latency/cost behavior; preserve M5 redaction, immutable result IDs, and credential boundaries.

## P2-1 exit gate

P2-1 is complete when both real adapters work through the existing M7 interfaces; provider wire formats are accepted by the selected model's Structured Outputs path and every returned object still passes local closed-schema validation; the controlled local end-to-end task completes protected MCP exploration, locator acceptance, and two deterministic replays; ambiguous/unsupported and provider failure paths retain typed records; and targeted injection and authority-boundary regressions pass. The normal offline suite remains credential-free. Record the exact model/configuration used for the live proof and any environment limitation. A credentialed provider call is required to claim the *real* adapter path is verified.

## Implementation decisions still open

- Choose the minimal Node Responses client (official SDK or direct HTTP) in B, including its retry and abort behavior. Do not add another model framework.
- Choose the exact strict provider wire schema and null/optional-field normalization in A. It must represent the approved closed variants faithfully; a provider-incompatible schema is a package blocker, not grounds to loosen domain validation.
- Choose local configuration names and the narrow sanitized provider-diagnostic sink in B/C. Credentials must be external to requests and artifacts; diagnostic fields must correlate with existing TestSpec/attempt IDs where available.
- Choose a bounded output-token limit and any lower provider-side timeout in B/C that fit M7's existing response and deadline bounds. Do not alter M7 retry or decision-count policy to accommodate provider defaults.

## Deferred beyond P2-1

P2-2 owns the local task-entry workflow and headed observation. P2-3 owns Python subprocess envelopes. Public-web validation is the Phase 2 acceptance gate after those integrations, not P2-1's local fixture proof. Optional `.spec.ts` review export is P2-4. This plan adds no product UI, independent service, browser viewing path, arbitrary model tool calls, or alternate replay engine.

**Recommended first implementation task:** P2-1A. Its strict provider schema bridge is the prerequisite for reliable Responses calls and protects the closed M7/TestSpec contracts before live model wiring begins.
